- 기준 브랜치: `main`
- 설계 상태: 검토 대기
- 범위: A16의 Podroid/Alpine 호스트에서 실행하고 기존 Debian/Docker 개발 환경과 공존하는 로컬 중심 자동 개발 관리자
- 비목표: NeoOS 웹/Vercel 구조 복원, 기존 OS/AI 설치 스크립트 전면 재작성, 사용자 승인 없는 운영 배포

## 1. 목적과 성공 기준

사용자가 지정한 NeoOS 개발 목표를 작업 단위로 나누고, 코드 변경·테스트·실패 분석·제한된 자동 수정·재검증을 수행하며, 모든 결과를 복구 가능한 기록으로 남기는 로컬 실행 도구를 설계한다.

성공 기준:
1. Android ARM64의 Podroid/Alpine에서 사용할 수 있고, 필요한 경우 기존 Debian/Docker 컨테이너를 테스트 실행 환경으로 활용한다.
2. 기존 사용자 변경 사항과 프로젝트 데이터는 보존된다. 기본 브랜치에 직접 쓰지 않는다.
3. 각 작업의 변경 파일, 테스트 명령, 출력, 재시도 횟수 및 종료 사유가 기록된다.
4. 테스트 실패 시 최대 3회의 자동 수정 시도 후 실패 상태로 멈춘다.
5. 각 실행의 절대 시간 한도는 24시간이며, 한도 도달 시 새로운 작업을 시작하지 않고 안전한 종료·기록을 수행한다.
6. 로컬 테스트와 별도 승인 없이는 병합 또는 프로덕션 배포가 실행되지 않는다.
7. 필수 경로는 무료·카드 불필요를 우선하며, 유료 API/서비스로 자동 전환하지 않는다.

## 3. 아키텍처

### 3.1 로컬 오케스트레이터

Python 기반의 작은 CLI 관리자로 구현한다. 기능은 다음 모듈로 나눈다.

- **Run controller:** 실행 시작/마감 시각, 중지 신호, 전체 시간 한도 관리.
- **Task queue:** 사용자 목표와 작업 상태를 관리하고, 완료·실패·대기 상태를 구분.
- **Workspace guard:** 저장소 경로, 현재 브랜치, 미커밋 변경 사항, 허용된 파일 경로를 검사.
- **Git worker:** 전용 작업 브랜치와 커밋을 관리하며 기본 브랜치 직접 수정 방지.
- **Test runner:** 저장소에 정의된 테스트 명령만 명시적 허용 목록에 따라 실행하고 제한 시간 내 결과 수집.
- **AI adapter:** 선택적으로 설정된 모델 제공자에 작업 계획/오류 분석/패치 제안을 요청하는 인터페이스. 제공자별 연결 정보는 환경변수 또는 로컬 비밀 저장 위치에서 읽고 저장소·로그에는 기록하지 않는다.
- **Retry controller:** 실패 분류, 최대 3회 자동 수정 시도, 동일 오류 반복 감지.
- **Checkpoint/report store:** 원자적 상태 저장, 테스트 출력, 변경 요약, 최종 보고서 기록.
- **Deployment gate:** 배포 준비 여부를 검사하되 실제 병합과 프로덕션 배포는 사람의 별도 승인 없이는 수행하지 않는다.

### 3.2 데이터 흐름

1. 사용자가 목표와 허용 범위를 입력한다.
2. 사전 점검이 저장소 상태와 리소스 여건을 검사한다.
3. 변경 사항이 있거나 상태가 불명확하면 쓰기 작업을 시작하지 않고 중단한다.
4. 관리자는 전용 브랜치에서 작은 작업을 하나씩 수행한다.
5. 허용된 테스트를 실행하고 결과를 체크포인트에 저장한다.
6. 실패 시 오류 로그에서 비밀정보를 제거한 뒤 분석하고, 범위 내 수정만 재시도한다.
7. 테스트 통과 시 변경 요약과 검증 결과를 생성한다.
8. 병합/배포는 승인 대기 상태로 남긴다.

## 4. 기존 프로젝트 보호

- 기본 브랜치 `main`에서 코드 변경 또는 자동 커밋을 하지 않는다.
- 시작 전 `git status --porcelain` 및 현재 브랜치를 확인한다. 작업 트리에 사용자 변경 사항이 있으면 기본적으로 실행을 거부한다. 별도 임시 worktree를 안전하게 만들 수 있는 경우에도 기존 변경 파일은 복사·수정하지 않는다.
- 작업 브랜치는 기능별로 분리하며, 기존 브랜치 이름을 강제로 재설정하지 않는다.
- 허용 경로 밖의 변경, 예기치 않은 파일 삭제, 서브모듈/잠금 파일의 광범위한 변경이 감지되면 중단한다.
- `git reset --hard`, `git clean -fd`, 임의 삭제, 강제 푸시, 비밀정보 파일 열람/업로드를 자동 실행하지 않는다.
- 테스트와 패치 적용은 저장소 내부의 격리된 작업 디렉터리에서 수행한다. Docker를 사용할 때는 기존 컨테이너·볼륨을 삭제하거나 재생성하지 않고, 별도 테스트 리소스가 필요한 경우 사용자 승인을 요구한다.
- GitHub 인증 토큰, OAuth 정보, API 키, 쿠키, 개인키 및 환경변수 파일을 로그나 커밋에 포함하지 않는다.
- 백업 성공 여부를 확인하지 못한 경우 백업 완료로 표시하지 않는다.

## 5. 실행 시간·재시도·복구

- 기본 실행 상한: 24시간. 실행 시작 시각과 절대 마감 시각을 상태 파일에 저장한다.
- 마감 시각 도달 시 신규 작업/재시도를 금지하고 현재 명령의 제한 시간 내 종료를 기다린 후 상태를 기록한다.
- 기본 자동 수정 한도: 작업당 3회. 동일 오류가 반복되거나 범위 밖 변경을 요구하면 즉시 중단한다.
- 각 테스트 명령은 별도의 실행 시간 제한을 가진다. 테스트가 멈추면 하위 프로세스를 정리하고 실패 로그를 저장한다.
- 상태 파일은 임시 파일에 쓴 뒤 원자적으로 교체한다. 상태에는 실행 ID, 목표, 브랜치, 단계, 시도 횟수, 마감 시각, 테스트 요약 및 최근 체크포인트를 포함한다. 인증정보와 전체 환경변수는 저장하지 않는다.
- 재시작 시 마지막 체크포인트와 Git 상태를 재검사한다. 상태와 저장소가 일치하지 않으면 자동 재개하지 않고 사용자 검토를 요청한다.
- Android/Podroid/Docker 프로세스가 OS에 의해 종료되거나 기기 전원이 꺼진 동안 실행이 지속된다고 보장하지 않는다. 재개 기능은 관리자가 다시 실행된 뒤에만 동작한다.

## 6. AI 제공자와 비용 정책

- AI 기능은 어댑터 인터페이스 뒤에 둔다. 특정 유료 제공자를 코드에 고정하지 않는다.
- 기본 설정은 사용자가 직접 구성한 무료 또는 로컬 제공자만 허용한다. 제공자가 없거나 할당량/네트워크 오류가 발생하면 무단으로 다른 유료 제공자에 전환하지 않는다.
- 모델 호출 없이 가능한 Git 상태 검사와 테스트는 계속 사용할 수 있다. AI가 없어 작업 계획/수정이 불가능하면 현재 상태를 저장하고 사용자에게 알린다.
- 모델 출력은 신뢰할 수 없는 제안으로 취급하며, 실행 명령은 허용 목록과 정책 검사 후에만 실행한다.
- API 키는 환경변수 또는 로컬 전용 설정으로 제공하며, 저장소 파일과 로그에서 제외한다.

## 7. 테스트 및 품질 게이트

각 작업은 다음 검증을 실행 가능한 범위에서 수행한다.
1. Python 문법/구문 검사.
2. 기존 단위 테스트: `python3 -m unittest test_neoos -v`.
3. 관련 프로젝트별 테스트 및 정적 검사(저장소에 존재하고 실행 가능한 경우).
4. 변경 파일 범위 검사와 비밀정보 누출 검사.
5. 필요한 경우 ARM64/Podroid/Debian/Docker 호환성 확인.

테스트가 실행되지 않았거나 환경 때문에 건너뛴 경우 이를 성공으로 표시하지 않는다. 기준 브랜치에서 기존 테스트가 실패하면 새 변경의 실패와 분리해 보고한다. 테스트 결과는 명령, 종료 코드, 시작/종료 시각, 요약을 포함한다.

## 8. 배포 및 GitHub 연동

- 초기 버전은 로컬 실행과 보고서 생성에 집중한다.
- 원격 브랜치 푸시와 Pull Request 생성은 설정 및 명시적 허용이 있을 때만 수행한다.
- 기본 브랜치 병합, 릴리스, Vercel/Render 프로덕션 배포, 서비스 재시작, 데이터 변경은 별도 사람 승인 대상이다.
- 배포 전에는 테스트 성공, 변경 범위 확인, 비밀정보 검사, 대상 환경/도메인 확인이 필요하다.
- 배포 후에는 실제 배포 식별자와 상태를 조회해 확인한다. 배포 메타데이터가 READY라는 사실만으로 애플리케이션 정상 동작을 단정하지 않는다.
- 연결 실패, 권한 부족, 무료 한도 불명확 시 배포를 중단하고 이유를 보고한다.

## 9. 리소스 및 중단 조건

A16의 CPU, 메모리, 저장 공간은 제한적이므로 실행 전 디스크 여유, 메모리, Docker 상태를 확인한다. 임계치 설정은 구현 단계에서 실제 기기 값을 확인한 뒤 정한다. 메모리 부족, 저장 공간 부족, 반복적인 테스트 시간 초과, 네트워크 불안정, 예기치 않은 저장소 상태, 승인 범위 밖 작업은 중단 사유다. 기존 AI 도구나 Debian/Docker 데이터 정리를 자동으로 시도하지 않는다.

## 10. 범위 밖

- 사용자 승인 없는 `main` 병합 또는 프로덕션 배포
- 무제한 반복, 무제한 모델 호출, 유료 서비스로 자동 전환
- 운영 데이터 삭제/마이그레이션

- 휴대폰 전원 종료나 Android 강제 종료 중에도 실행된다는 보장
- 현재 환경에서 아직 검증되지 않은 서비스/모델의 무료 사용 가능성에 대한 보장

## 11. 구현 완료 조건

- 안전한 사전 점검에서 사용자 변경 사항을 감지하면 파일을 수정하지 않고 중단한다.
- 기본 브랜치 직접 변경을 거부하고 전용 브랜치만 사용한다.
- 모의 테스트 실패를 주입했을 때 최대 3회 후 종료하고 실패 보고서를 남긴다.
- 실행 마감 시각에 신규 작업을 시작하지 않는다.
- 중단 후 재실행 시 일관된 체크포인트는 복구하고 불일치 상태는 중단한다.
- 로그/보고서에 비밀정보가 포함되지 않는다.
- 기존 NeoOS 테스트와 새 관리자의 테스트를 모두 실행해 실제 결과를 기록한다.
- 배포는 승인 없이는 실행되지 않는다.
