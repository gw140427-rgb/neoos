# NeoOS AI 자동 개발 시스템 설계 명세 (초안)

- 상태: 설계 기준 승인, 구현 전 명세
- 실행 기준: Galaxy A16 / Podroid Alpine ARM64 / Docker 안의 Debian Linux
- 우선순위: 무료·카드 불필요, 기존 프로젝트 보호, 로컬 제어 우선
- 범위: 웹/Vercel 서버를 새로 만들지 않고 현재 NeoOS Linux/Docker 방향을 유지한다.

## 1. 목표

사용자가 개발 목표를 입력하면 시스템이 이를 작은 작업으로 나누고, 제한된 범위에서 코드를 변경하고, 테스트를 실행한다. 실패하면 로그를 분석해 수정안을 시도하고 다시 테스트한다. 정해진 반복 횟수나 시간에 도달하면 성공 여부와 무관하게 멈추고 결과를 기록한다.

이 시스템은 무한 자율 실행을 보장하지 않는다. 전원, Android 백그라운드 제한, 네트워크, 모델 호출 한도, 컨테이너 리소스의 영향을 받는다.

## 2. 실행 환경

Podroid Alpine Linux
└── Docker
    └── neoos-linux (Debian)
        └── NeoOS AI 자동 개발 CLI/작업 관리자

- ARM64 및 Debian/Termux 호환성을 우선한다.
- AI 모델 제공자는 선택형 어댑터로 분리한다. 필수 API 키나 유료 서비스를 기본값으로 요구하지 않는다.
- 로컬 모델이 없거나 성능이 부족하면 시스템은 자동으로 무단 유료 호출을 하지 않고, 사용 가능한 무료 제공자 설정 또는 수동 실행을 요구한다.
- 현재 Debian 컨테이너의 읽기 전용 루트 파일시스템과 리소스 제한을 유지한다.

## 3. 구성 요소

1. Goal Manager: 목표, 완료 조건, 제한 시간, 최대 반복 횟수를 저장한다.
2. Task Planner: 목표를 검증 가능한 작은 작업으로 나눈다.
3. Workspace Guard: 허용된 프로젝트 디렉터리만 변경 대상으로 허용한다.
4. AI Provider Adapter: 선택된 모델과 통신한다. 키와 비밀값은 로그에 기록하지 않는다.
5. Patch Executor: AI가 제안한 변경사항을 별도 작업 브랜치/작업 디렉터리에 적용한다.
6. Test Runner: 프로젝트에 정의된 테스트를 실행하고 종료 코드와 로그를 수집한다.
7. Failure Analyzer: 테스트 실패 로그를 요약하고 다음 수정 시도를 위한 입력을 만든다.
8. Checkpoint Manager: 각 반복 전후의 변경사항, 테스트 결과, 커밋 또는 백업 상태를 기록한다.
9. Stop Controller: 반복 횟수, 실행 시간, 실패 연속 횟수, 디스크 여유 공간, 사용자 중지 요청을 확인한다.
10. Report Writer: 목표별 상태, 변경 파일, 테스트 결과, 미해결 문제를 Markdown으로 기록한다.

## 4. 작업 상태 흐름

PLANNED -> PRECHECK -> IMPLEMENT -> TEST -> (PASS -> REVIEW_REQUIRED)
                              (FAIL -> ANALYZE -> RETRY)
모든 상태에서 제한 초과, 보호 규칙 위반, 사용자 중지 요청이 발생하면 STOPPED로 전환한다.

- 테스트 성공은 목표 전체 완료와 동일하지 않다. 완료 조건을 별도로 평가한다.
- 기본 최대 수정 반복: 3회.
- 기본 실행 시간 제한: 30분.
- 연속 실패 한도: 3회.
- 값은 설정으로 조정할 수 있지만 기본값은 안전 우선으로 둔다.

## 5. 보호 정책

- 기존 파일을 삭제하거나 덮어쓰기 전에 백업/버전 관리 상태를 확인한다.
- 작업 트리의 사용자 변경사항을 자동으로 reset, checkout, clean 또는 덮어쓰지 않는다.
- 기본 작업은 별도 Git 브랜치에서 수행한다. 기본 브랜치에 자동 push/merge하지 않는다.
- 비밀값, 토큰, .env 파일, SSH 키, 계정 파일을 모델 입력이나 로그에 포함하지 않는다.
- 허용 목록 밖의 경로 수정, 권한 상승, 호스트 경로 마운트, Docker 소켓 접근, 네트워크 공개, 패키지 설치, 배포 및 데이터 삭제는 기본 거부한다.
- 셸 명령은 임의 문자열을 무제한 실행하지 않고 승인된 명령 집합과 실행 시간 제한을 사용한다.
- 위험 작업은 사용자의 명시적 승인을 요구한다.
- 디스크 여유 공간이 설정 임계치 아래로 내려가면 새 반복을 시작하지 않는다.
- 취소 신호를 받으면 현재 명령을 종료하고 상태를 기록한다.

## 6. 목표 입력 형식

각 목표에는 다음 필드가 있다.

- title: 짧은 목표 이름
- description: 만들거나 고칠 내용
- acceptance_criteria: 검증 가능한 완료 조건 목록
- workspace: 허용된 프로젝트 경로
- test_command: 프로젝트에서 허용된 테스트 명령
- max_iterations: 기본 3
- time_limit_minutes: 기본 30
- network_policy: 기본 deny 또는 사용자 설정에 따른 제한 허용
- require_review: 기본 true

입력이 불완전하거나 완료 조건이 검증 불가능하면 코드를 변경하기 전에 질문하거나 계획만 출력한다.

## 7. 로그와 결과

각 실행은 타임스탬프, 목표 ID, 작업 ID, 수정 파일 목록, 테스트 종료 코드, 짧은 오류 요약, 반복 횟수, 중단 사유를 기록한다. 비밀값과 전체 환경 변수는 기록하지 않는다.

보고서에는 다음을 포함한다.
- 목표 및 완료 조건
- 수행한 단계
- 변경된 파일
- 테스트 명령과 성공/실패
- 남은 문제
- 중단 사유와 다음 안전한 작업

## 8. 단계별 구현 계획

1. 명세 및 안전 정책 문서화.
2. 읽기 전용 사전 점검 CLI 구현.
3. 목표 파일과 상태 저장소 구현.
4. 보호된 작업 디렉터리와 반복 제한 구현.
5. 테스트 실행기와 보고서 구현.
6. 모의 AI 어댑터로 실패/재시도 흐름 테스트.
7. 실제 AI 제공자 어댑터를 선택적으로 추가.
8. ARM64 Debian에서 테스트하고 기존 NeoOS 테스트와 회귀 검증.

## 9. 첫 구현의 완료 조건

- 기본 명령이 현재 환경과 저장소 상태를 읽기만 하고 출력한다.
- 사용자 파일을 변경하거나 네트워크 요청을 하지 않는다.
- Python 단위 테스트가 통과한다.
- 반복 횟수 및 시간 제한이 테스트로 검증된다.
- 위험 경로 및 비밀값이 차단된다.
- 기존 NeoOS CLI, installer, compose 구성의 동작을 변경하지 않는다.

## 10. 알려진 한계

Android는 프로세스와 백그라운드 작업을 종료할 수 있다. 따라서 장시간 작업은 컨테이너 안에서도 항상 실행된다고 보장할 수 없다. 안정적인 24시간 작업에는 계속 켜져 있는 별도 호스트가 필요하지만, 이번 설계는 현재 Podroid 환경에서 안전하게 재개할 수 있는 구조를 우선한다.
